# PART I — BUILD & TECHNICAL SPECIFICATION

BUILD PROMPT FOR ANTIGRAVITY
Project: Synapse_AI — AI Technical Interview Agent (fully functional)

Paste everything below into Antigravity as the task. It is self-contained: stack, file structure, API contract, data files, agent logic, UI spec, and acceptance criteria are all included so nothing needs to be inferred.

0. Goal

Build a fully functional, deployable web application called Synapse_AI: a conversational AI agent that conducts a realistic, multi-turn technical interview with a candidate based on their AI Cohort progress, then produces structured feedback. One HTTP endpoint drives the entire backend. The frontend is a polished, desktop-first, light/dark-themeable UI.

This must actually work end-to-end — real LLM calls, real session state, real adaptive question selection from the provided curriculum, not a mocked demo.

1. Tech stack (use this exact stack unless there's a strong reason not to)
Framework: Next.js 14+ (App Router), TypeScript, single deployable app (frontend + API routes together — simplest path to "expose one endpoint")
Styling: Tailwind CSS with CSS variables for theming (tokens given in §5)
State: React state/hooks on the client; server-side session state kept in an in-memory Map<sessionId, SessionState> in a singleton module (acceptable per spec — "no persistent user accounts / long-term history" required, so in-memory is correct, not a shortcut)
LLM provider: Anthropic Claude via @anthropic-ai/sdk, model configurable via process.env.ANTHROPIC_MODEL (default to a current Claude model). Provide a thin lib/llm.ts wrapper so the provider can be swapped later.
No database, no auth library, no ORM — explicitly out of scope. Don't add Supabase, NextAuth, Prisma, etc.
Package manager: npm
2. Provided data files (place at project root under /data, load at server startup)
/data/curriculum.json — 31 days, 8 modules, each day has title, type, tools[], objectives[]
/data/candidates.json — array of candidate profiles, each with member (id, name, jobRole, yearsExperience, education, status), missions[] (day, title, passed/skipped, attempts), signals (commitDays, missionsCompleted, missionsFirstTry)

Load both once at server start into memory (lib/data.ts). All question generation and personalization must read from these — never hardcode curriculum content or candidate content in prompts as static strings.

3. API contract — implement exactly (this is graded)

Endpoint: POST /api/interview — no auth.

Turn 1 — Start

Request:

json
{ "sessionId": "abc-123", "candidate": { ...one record from candidates.json (member + missions + signals) } }

Response:

json
{ "reply": "Welcome. Let's begin your interview.", "done": false }

On this call: create a new SessionState keyed by sessionId, store the candidate object, compute the initial difficulty + focus days (see §4.2), and generate the first question. The reply for turn 1 can be a short welcome — but store the actual first question as the next message, OR (preferred, more realistic) have the welcome message already contain the first question so the candidate isn't stuck. Decide one approach and be consistent; recommended: welcome + first question combined in one reply string.

Turn 2..N — Conversation

Request:

json
{ "sessionId": "abc-123", "message": "the candidate's answer text" }

Response:

json
{ "reply": "next question or follow-up", "done": false }

Server must:

Look up session by sessionId. If missing, return a clear error (400) — don't silently create a blank session.
Append the candidate's message to that session's transcript.
Decide: ask a follow-up on the previous answer, or move to a new curriculum day/question. Follow-up logic must actually inspect the previous answer's content (vague, shallow, contradicts a claimed skill, mentions a tool worth probing) — not be random.
Track daysCovered: Set<number> on the session. Must reach ≥4 distinct curriculum days and the session must ask ≥8 questions total (follow-ups count toward total question count but not toward distinct-day count) before it's allowed to end.
Return next reply.
Final turn — End

When the session has satisfied the minimum (≥8 questions, ≥4 distinct days) AND the agent decides the interview is sufficiently complete (don't just hard-stop at exactly 8 — allow natural closure, cap around 10–15), respond:

json
{
  "reply": "Interview completed.",
  "done": true,
  "feedback": {
    "summary": "string",
    "strengths": ["string", "..."],
    "gaps": ["string", "..."],
    "next": ["string", "..."]
  }
}

feedback must be generated by the LLM from the actual transcript of this session — never templated/generic text. Each array should have 3–6 concise, specific, actionable items referencing real things the candidate said or curriculum topics they were weak/strong on.

Error handling
Malformed request body → 400 with { "error": "..." }
Unknown sessionId on a continuation turn → 400
LLM provider failure → 502 with { "error": "..." }, and do NOT drop the session state — the client can retry the same turn.
4. Interview agent logic (this is the core of the grade — build it carefully)
4.1 System prompt for the interviewer LLM

Construct a system prompt per session (built once at session start, reused every turn) that includes:

The candidate's member info (role, years experience, education)
A structured summary of their missions[]: which curriculum days they passed (with attempt counts — high attempts = weaker signal even if eventually passed), which they skipped
Their signals (commitDays, missionsCompleted, missionsFirstTry)
The relevant slice of curriculum.json — at minimum, the modules/days corresponding to their completed missions, so the interviewer can ask about real content they covered (objectives, tools) rather than generic AI trivia
Explicit behavioral instructions:
"You are conducting a real technical interview, not reading a script. Ask one question at a time."
"Prioritize topics the candidate passed with multiple attempts (possible weak spots) and topics with high signal (things to validate depth on), and touch on skipped topics briefly to check for gaps."
"After each answer, decide whether to ask a natural follow-up probing deeper, or move to a new topic. Vary this — don't follow up on every single answer."
"Reference specific tools/concepts from the curriculum days provided — never ask about topics the candidate never covered."
"Keep questions realistic for the candidate's stated experience level and job role."
"You must cover at least 4 distinct curriculum days and ask at least 8 questions total before ending."
"When ending, produce feedback strictly in the required JSON shape, grounded only in what the candidate actually said."
4.2 Adaptive difficulty

Compute a difficulty label (beginner / intermediate / advanced) server-side from the candidate's signals and missions[] before the interview starts (e.g., high missionsFirstTry ratio + low skips + high commitDays → advanced). Feed this label into the system prompt so question depth matches it. Store it on the session and include it in the final feedback context (even though the response schema in §3 doesn't have a dedicated difficulty field — fold the difficulty context into summary so it's visible, e.g. "Interviewed at Advanced difficulty based on strong first-attempt performance.").

4.3 Session state shape (server-side, in-memory)
ts
type SessionState = {
  sessionId: string;
  candidate: CandidateRecord;
  difficulty: "beginner" | "intermediate" | "advanced";
  systemPrompt: string;
  transcript: { role: "interviewer" | "candidate"; content: string }[];
  daysCovered: Set<number>;
  questionCount: number;
  createdAt: number;
}
4.4 Turn-by-turn model call pattern

Each turn, call the LLM with: system prompt + full transcript so far (as alternating messages) + the new candidate message. Ask the model to respond with both its next reply text and structured metadata (which curriculum day the question targets, whether it's a follow-up, whether it's ready to end) using a JSON-mode/tool-call pattern so the server can reliably update daysCovered/questionCount and decide when done: true is appropriate — don't parse free text with regex. Suggested approach: use Claude's tool-use feature with a tool like submit_turn(reply: string, targetDay: number | null, isFollowUp: boolean, readyToEnd: boolean), and a separate tool submit_feedback(summary, strengths[], gaps[], next[]) for the final turn.

# PART II — COMPLETE INTERFACE DESIGN SPECIFICATION

Synapse_AI — Interview Agent
Complete Interface Design Specification (for Antigravity build)

Version 1.0 · August 2026

0. What this document is

This is a build-ready design spec, not the full Synapse_AI product. It takes the branding, visual language and IA style of the Synapse_AI PRD and wraps it tightly around the actual hackathon deliverable: a conversational AI interview agent that talks to a candidate, adapts using the 31‑day curriculum, and produces structured feedback through a single API contract.

In scope: Landing → "Upload Resume" (cosmetic front-end for picking a candidates.json profile) → Interview Setup → Live Interview → Report/Transcript.

Explicitly out of scope (per hackathon rules — do not build): real authentication, real resume parsing/OCR, a persistent multi-session dashboard, cross-session interview history, voice/video, mobile app.

The trick: every screen that looks like it belongs to the bigger Synapse_AI product is real UI — but the data behind it always resolves to curriculum.json + one record from candidates.json, and the entire runtime talks to exactly one endpoint: POST /api/interview, per technical-spec.md.
